# Workflow 02: 交互式访谈

> 此文件是 SKILL.md 的展开。在执行 Phase 1.1b 时进入本文件,按下面的协议进行。

## 目的与约束

访谈是为了 **填补扫描无法回答的问题**,不是为了走流程。具体来说,扫描能告诉你"项目里有什么",访谈要告诉你:

- 为什么是这样
- 团队和使用者的实际诉求
- 风险偏好和硬约束
- 哪些痛点是真痛点,哪些是被夸大的

**核心约束**:

- **一次一个问题**,等用户回答完再问下一个。不要列清单。
- **5-8 个问题为硬上限**。超过用户就会烦,质量反而下降。
- **问题必须基于扫描结果裁剪**。扫描已经能回答的事不要问。
- **新信息出现就追,不要执着清单**。用户提到一个之前没料到的痛点,立刻深挖,该跳过的常规问题就跳过。
- **不耐烦就停**。问够了用户体感会变化,这是关键信号。

## 必备信息清单(8 项)

访谈结束时,内部应该收集到这 8 项中至少 6 项的明确答案。缺失项在处方时明确标注 `[unknown]`。

| 编号 | 信息项 | 用途 |
|---|---|---|
| I1 | 项目阶段(原型 / 小团队 / 生产) | 定位矩阵的纵轴 |
| I2 | 主要使用平台(Claude Code / Codex / 混合) | 影响 hook 与配置建议 |
| I3 | 团队规模与协作模式 | 影响组织层投资优先级 |
| I4 | Agent 当前使用频率与典型场景 | 判断有没有真实需求 |
| I5 | 最频繁的失败模式(具体例子) | 处方的主要锚点 |
| I6 | 风险偏好与不可让 agent 自动做的事 | Permission tier 设计依据 |
| I7 | 本次改造的目标(止血 / 结构化 / 上规模) | 决定路线图分阶段 |
| I8 | 改造投入意愿(时间、人力上限) | 路线图节奏控制 |

I1、I5、I6、I7 是 **必须问到** 的——缺这四项中任何一项,处方都会失真。其余四项可以从扫描或推断得到,缺失可接受。

## 起手第一问:基于扫描结果决定

不要总是用同一个开场。根据扫描结果选择最有信息量的切入点:

| 扫描发现 | 起手问 | 优先采集 |
|---|---|---|
| 仓库完全没有 agent 痕迹 | "你这次想接入 agent 工作流,主要想用它做什么?" | I7 → I4 |
| 有 CLAUDE.md / AGENTS.md 但很短(< 50 行)、无 hook | "你现在用 agent 用得怎么样?哪些场景顺手哪些不顺?" | I5 → I4 |
| 有完整 .claude/ 或 Codex 配置但 PR 历史频繁 revert | "最近 agent 让你最头疼的是哪类问题?" | I5 → I8 |
| CLAUDE.md / AGENTS.md > 200 行、规则密集 | "这些规则是怎么积累起来的?最近一次大改是什么时候?" | 触发 I5 + I7 的对比 |
| 有 docs/ 但结构散乱 | "你的 docs/ 当前是给人看的还是给 agent 看的?或者两者?" | 触发知识库定位讨论 |
| 团队仓库(有多个 contributor) | "团队有多少人在用 agent?他们之间有共识吗?" | I3 → I6 |

起手问的目的是 **让用户进入语境**,同时一次性激活 2 项信息。如果起手问只能采集 1 项,换一个。

## 各维度的问题池与追问树

下列问题不是清单,是池子。**根据起手问的回答选下一个,而不是按顺序问。**

### A. 阶段与目标(对应 I1、I7)

- A1. "项目目前处于什么阶段?个人原型、小团队在用、还是生产线上?"
- A2. "团队多少人会接触 agent 的产出?"
- A3. "这次改造主要想解决什么?"(追问树见下)

**A3 追问树**:

```
用户答 → 下一问
─────────────────────────────────────────────
"减少 agent 错误" → 跳 B1(深挖最具体的错误)
"想引入更多 agent 工作" → 跳 C1(确认约束) 
"团队要规范化" → 跳 D2(组织层目标)
"老板要看效果" → 跳 D3(度量诉求)
模糊 / 没想清楚 → 提醒可能不需要 harness,先反向确认有没有具体痛点
```

### B. 痛点识别(对应 I5)

- B1. "最近一周,agent 让你最头疼的一件事是什么?给个具体例子。"
- B2. "这是偶发还是反复出现?最近出现过几次?"
- B3. "你现在怎么应对这个错误?改了 prompt?加了规则?手工 revert?"
- B4. "如果不解决这个问题,最坏会怎样?"

**B 系列追问规则**:

- B1 答得模糊("各种乱七八糟问题") → 强制具体化:"最近一次具体是哪个 commit / 哪个 PR?"
- B2 答"只出过一次" → 标记 **可能不构成模式**,提醒在处方中说明
- B2 答"反复出现 3 次以上" → 这是处方的核心锚点,问 B3、B4 深挖
- B3 答"已经加了 prompt 规则" → 询问规则放在哪一层(CLAUDE.md / 文档 / 测试),这暗示 L0-L4 的现状

### C. 约束识别(对应 I6)

- C1. "有哪些操作你绝对不允许 agent 自动执行?"
- C2. "团队里有没有人对 agent 有顾虑?具体顾虑是什么?"
- C3. "有合规、安全、审计上的硬约束吗?"
- C4. "production 环境 agent 能不能直接动?"

**C 系列追问规则**:

- C1 答"什么都不允许,全要 ask" → 标记 permission tier 过严的风险,问 C2 深挖原因
- C1 答"随便,agent 想干啥都行" → 标记 permission tier 过松,问 C3 / C4 看有没有硬约束被忽略
- C2 有具体顾虑 → 把顾虑作为 permission tier 的设计依据
- C3 有合规约束 → 标记不可逆约束,处方时必须显式覆盖

### D. 现有状态深挖(对应 I4、I8 及组织诉求)

- D1. "现在的 CLAUDE.md / AGENTS.md 是怎么演化来的?最近一次大改是什么时候、为什么?"
- D2. "如果让一个新人(或新的 agent)接手这个项目,你担心他/它会做错什么?"
- D3. "你最满意的 harness 配置是哪一块?最不满意的是哪一块?"
- D4. "你打算给这次改造多少时间和人力?"
- D5. "你的成功标准是什么?怎么知道改造做对了?"

**D 系列用法**:

- D1 是诊断"规则爆炸"是否存在的关键问题——如果用户答不上来"为什么这一条在",说明规则失去了可追溯性
- D2 暴露用户的隐性知识——这些通常是需要进 L0/L1 的硬约束
- D3 提供用户的主观满意度信号,帮助判断哪些 gap 是 🔴 哪些是 🟡
- D4、D5 控制路线图的节奏与可衡量性

## 不要问的问题(反模式)

| 反模式 | 为什么不问 | 替代 |
|---|---|---|
| "讲讲你的项目" | 太宽泛,用户给的信息无法定位 | 直接问具体维度(阶段、痛点) |
| "你觉得需要 hook 吗?" | 引导性问题,用户没决策依据 | 问痛点和约束,自己推 |
| "你的 CLAUDE.md 多少行?" | 扫描就能看出来 | 跳过 |
| "你用的是 Python 还是 Go?" | 与 harness 无关 | 除非直接影响诊断,否则跳过 |
| "你看过 v2 doc 吗?" | 用户教育不在本 skill 范围 | 直接给方法论结论 |
| "harness 是什么你了解吗?" | 同上 | 假定用户够格,有概念 gap 就在回答中补 |
| "你觉得自己的 harness 怎么样?" | 主观、无锚点 | 问 D3(最满意/不满意),有具体对象 |

## 追问的微观技巧

- **具体化**:用户给抽象答案("agent 经常出错")→ 立刻追"最近一次具体是?"
- **数字化**:用户给模糊频率("挺多的")→ 追"最近一周大概几次?"
- **挖动机**:用户给方案性答案("我想加一个 hook")→ 追"这个 hook 是想解决什么具体问题?"——避免被用户的方案带跑
- **挖反例**:用户给绝对断言("我们绝对不要 X")→ 追"有过什么情况让你想破这个规则吗?"
- **挖隐性约束**:用户答案里出现专有词("我们的发布流程")→ 追这个流程的关键步骤,常有隐性 harness 约束

## 停止访谈的信号(任一满足即停)

1. **覆盖率达标**:必备 8 项中至少 6 项已答清楚,且 I1 / I5 / I6 / I7 全部覆盖
2. **边际递减**:连续两个问题没拿到新信息,只是变体重复
3. **硬上限**:已经问了 8 个问题
4. **用户不耐烦**:回答变短、出现"差不多就这样"、明显在抢着结束——**这是最重要的信号**,优先于其他
5. **用户主动结束**:"差不多了吧,你直接给我建议"——立即停止

停止后做一件事:**告诉用户访谈结束,确认是否还有想补充的**。例如:

> "信息够了。开始出处方前,你还有没有什么我没问到但你觉得重要的?"

这个开口给用户最后的补充机会,常常会拿到访谈中没问出来的关键信息。

## 访谈摘要(内部产物)

访谈结束后,在内部(不展示给用户)生成一份结构化摘要,作为 Phase 2 的输入:

```
## 访谈摘要

### 必备信息
- I1 阶段: [小团队 / 生产 / 原型 / unknown]
- I2 平台: [Claude Code / Codex / 混合 / unknown]
- I3 团队规模: [人数 + 协作模式 / unknown]
- I4 使用频率: [描述 / unknown]
- I5 主要痛点: [具体描述,带例子和频率]
- I6 不可逾越约束: [清单]
- I7 改造目标: [止血 / 结构化 / 上规模 / 其他]
- I8 投入意愿: [时间 + 人力 / unknown]

### 衍生信号
- 风险偏好: [保守 / 中等 / 激进]
- 隐性约束: [从 D2 等问题里挖出的]
- 用户主观满意度高/低的部分: [来自 D3]

### 缺失项
- [列出未拿到的 I 项,以及为什么没拿到——用户拒答 / 信息不存在 / 时间用完]
```

## 与 Phase 2 的衔接

带着这份摘要进入 Phase 2(处方)。如果 I1 / I5 / I6 / I7 任一缺失,处方阶段必须:

1. 在报告里显式说明"由于 X 信息缺失,本处方在 Y 方面给出的是通用建议而非项目特定建议"
2. 把"补齐 X 信息后重新评估"作为路线图的第 0 阶段

宁可显式标注信息不足,也不要凭直觉填空。
